# Splitaway: неизменяемая история — подготовка, 2026-10-01

Статус: аудит действующей БД выполнен только чтением. Миграция НЕ применена.
Не является отчётом об успешном внедрении или резервной копией БД.

## Подтверждено по метаданным production

- Проект Splitaway, PostgreSQL 17.
- `sync_trip_data(text,jsonb)` заменяет `treasury.settled_debts` целиком.
- Отдельного журнала событий в public нет.
- На trips, members, groups, expenses и treasury включён RLS, но роль anon
  имеет SELECT и политику SELECT USING (true). Изоляции чтения по поездке нет.
  Публичный anon key не является секретом и не заменяет проверку доступа.
- Серверная delete_expense проверяет приглашение поездки, но удаляет расход
  физически. Историю удалённых записей задним числом восстановить нельзя.
- На сервере есть миграции 014/015/016, отсутствующие в локальном наборе.
- Локально не найдены Supabase CLI, psql и Docker; backup/restore не проверены.
- ZIP исходников и APK не являются резервной копией базы.

## Требуемая модель (проект, ещё не реализовано)

1. Приватный журнал `trip_events`, доступный только через проверенные операции.
   Поля: event_id UUID, trip_id, trip_sequence BIGINT, operation_id UUID,
   event_type, entity_id, actor_member_id, server_recorded_at TIMESTAMPTZ,
   occurred_at (отдельная дата пользователя), payload_version, payload JSONB,
   reverses_event_id. Суммы — BIGINT cents, обязательный currency_code.
2. UNIQUE(trip_id, operation_id), UNIQUE(trip_id, trip_sequence).
   Индекс (trip_id, trip_sequence) для чтения страниц по курсору.
3. Каждая операция в одной короткой транзакции: проверить сессию и роль,
   заблокировать строку версии поездки, проверить operation_id и expected_version,
   рассчитать/валидировать сумму, добавить событие, обновить проекцию и версию.
4. Повторный operation_id с тем же запросом возвращает прежний результат.
   Тот же ID с другим содержимым возвращает OPERATION_CONFLICT.
   Идемпотентность проверяется до отклонения повторной операции из-за версии.
5. UPDATE/DELETE/TRUNCATE журнала запрещены прикладным ролям; защитные триггеры.
   Коррекция — новое связанное событие, а не замена старого. Администратор БД
   технически может менять схему; абсолютную неизменяемость от владельца БД
   не обещаем. Нужны контролируемые роли и резервные копии.
6. В события не включать invite/admin/session tokens, ключи и receipt base64.
   actor_member_id выводится из проверенной сервером сессии, а не S.me.
   claimed_device и публичное имя сами по себе не являются аутентификацией.
7. Начальные данные помечаются legacy_import с временем импорта. Не придумывать
   автора, точное время и прежние долги. Записи групповых взаимозачётов не
   представлять как отдельные фактические переводы.
8. Политика удаления поездки/персональных данных должна быть согласована отдельно:
   запрет удаления финансовой записи в UI не означает вечное хранение данных.

## Совместимость APK/PWA

- Архив читается из одного серверного API по курсору, выводится через textContent.
- Новая очередь хранит operation_id до подтверждения, повторяет тот же ID.
- Финансовые ответы не попадают в Service Worker static cache.
- Realtime — уведомление о новой версии, после него чтение сервера; не источник истины.
- Старый sync_trip_data не должен обходить журнал. Варианты: адаптер всех старых
  операций или отказ устаревшему клиенту с понятным требованием обновления.
- Не подключать новый frontend до готовности и тестирования API. Не заменять
  серверные гарантии локальным Object.freeze или скрытием кнопок.
- Чтение таблиц напрямую нужно заменить проверенным API до закрытия anon SELECT,
  иначе уже установленные APK потеряют доступ. Не закрывать права вслепую.

## Порядок внедрения и резервная копия

1. Подтвердить свежую копию схемы + данных + ролей действующей БД. Хранить приватно,
   вне Git, public, deploy и APK. Снять определения RPC, триггеров, RLS и grants.
2. Проверить восстановление в отдельной тестовой БД. Не создавать платную ветку
   или ресурс без согласования. Сохранить время копии и результат restore.
3. Сверить реальную схему и локальные миграции; создать миграцию штатным CLI.
4. На тестовой БД реализовать сессии/проверенное чтение, журнал и операции;
   проверить отрицательные сценарии и конкурентные транзакции.
5. Подготовить новую PWA/APK и совместимый переход старых клиентов.
6. После подтверждения применить production-миграцию в контролируемом окне.
7. Проверить два независимых клиента, затем релиз на устройствах.

## Обязательные тесты перед production

- Чужая поездка, случайный ID, неверный/истёкший/отозванный токен — отказ.
- Клиентские INSERT/UPDATE/DELETE/TRUNCATE журнала — отказ.
- Полное/частичное погашение, 1 цент, ноль, отрицательная сумма, переплата.
- Два одновременных погашения: нет потери событий и переплаты.
- Повтор запроса после потери ответа: одно событие, один финансовый эффект.
- Исправление/отмена расхода: старое событие остаётся, проекция корректируется.
- Сумма балансов равна нулю в cents; валюты не складываются без конвертации.
- Offline/reconnect, restart, realtime, пагинация без пропусков/дубликатов.
- Проверки на PWA и release APK, на двух устройствах и с семью языками.

## Откат

До записи событий: отключить новую функцию, откатить приложение на совместимую
версию; миграционные объекты удалять только при доказанном отсутствии записей.
После записи: остановить новые записи при необходимости, исправлять вперёд;
не удалять журнал и не восстанавливать старый snapshot поверх новых платежей.
Восстановление из backup требует сверки всех операций после его времени.

## Непроверенное

Backup/restore, новая SQL-модель, гонки настоящих транзакций, запрет изменения
журнала, истечение сессий и поведение двух устройств ещё не проверены.
Production-данные пользователей и токены при аудите не запрашивались.
